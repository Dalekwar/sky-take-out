## 1. 问题陈述

苍穹外卖是一个面向餐饮企业的在线外卖订购系统，涵盖顾客端（网站 + 小程序）、餐厅运营端和后台管理端三大模块。当前管理后台是整个系统的运营枢纽——**没有高效的后台，前台订单流转、菜品上下架、经营数据分析都无法闭环**。

具体来说，餐饮企业内部员工面临以下痛点：

- **订单处理效率低**：订单分散在不同渠道（网站/小程序），缺乏统一后台集中处理，容易出现漏单、错单、延迟派送；
- **菜品管理割裂**：菜品分类、菜品信息、套餐配置分散管理，上下架操作繁琐，无法快速响应营业策略调整；
- **人员管理不规范**：内部员工账号缺乏统一管理，权限不清晰，存在信息安全隐患；
- **经营数据不可见**：营业额、用户数、订单量等核心经营指标缺乏可视化统计，管理者"拍脑袋"决策而非数据驱动。

本功能模块（管理后台）的构建，旨在为餐饮企业提供一站式的运营管理工具，覆盖从员工管理到数据统计的完整运营链路。

## 2. 目标

### 用户目标（内部员工视角）

| 编号 | 目标                           | 衡量标准                     |
| -- | ---------------------------- | ------------------------ |
| U1 | 内部员工可安全登录系统并执行权限范围内的操作       | 登录成功率 ≥ 99%；越权访问拦截率 100% |
| U2 | 员工可在 30 秒内完成菜品/套餐的上下架操作      | 上下架平均操作耗时 < 30 秒         |
| U3 | 运营人员可在一个界面完成订单的查询→处理→状态更新全流程 | 订单处理平均耗时 < 2 分钟/单        |
| U4 | 管理者可查看当日营业额、订单量、用户数等核心经营数据   | 数据看板加载时间 < 3 秒           |

### 业务目标（企业视角）

| 编号 | 目标                  | 衡量标准                     |
| -- | ------------------- | ------------------------ |
| B1 | 统一管理所有渠道订单，减少漏单/错单率 | 漏单率 < 0.1%，错单率 < 0.5%    |
| B2 | 支撑餐厅日常运营的菜品/套餐快速调整  | 菜品变更后前台同步延迟 < 5 分钟       |
| B3 | 为管理层提供数据驱动的经营决策依据   | 管理后台日活（DAU）≥ 内部员工总数的 80% |

## 3. 非目标（Non-Goals）

以下内容**明确不在本版本范围内**，防止范围蔓延：

| 编号 | 非目标                  | 排除理由<span style="background-color:rgb(243, 245, 247)">员工角色体系</span> |
| -- | -------------------- | ------------------------------------------------------------------- |
| N1 | 不做顾客端（网站/小程序）的前台界面开发 | 顾客端为独立模块，由前端团队并行开发，不在后台 PRD 范围内                                     |
| N2 | 不做支付系统的底层接入开发        | 支付系统接入（微信/支付宝）作为独立技术模块，本 PRD 仅涉及后台对支付订单状态的展示与处理，不涉及支付网关对接           |
| N3 | 不做多餐厅连锁管理            | v1 仅支持单餐厅后台管理，连锁多门店管理为 v2 规划                                        |
| N4 | 不做员工绩效考勤模块           | 绩效/考勤属 HR 系统范畴，与外卖运营管理职责分离                                          |
| N5 | 不做智能推荐/营销自动化         | 智能推荐和营销自动化需要 AI 算法支撑，当前阶段数据量不足，列入 v3 远期规划                           |

## 4. 用户角色

> **已确认（Q1）**：员工角色体系确定为 3 种——管理员、运营人员、客服，不设"财务"角色。

| 角色       | 描述                      | 核心诉求                    |
| -------- | ----------------------- | ----------------------- |
| **管理员**  | 餐厅最高权限的内部员工，通常为店长或运营负责人 | 管理员工账号、查看全部数据、处理异常订单和投诉 |
| **运营人员** | 负责菜品、套餐、分类的日常维护         | 快速上下架菜品、调整分类、管理套餐       |
| **客服**   | 负责订单咨询和投诉处理             | 查询订单状态、处理取消/退款审核、记录投诉     |

## 5. 用户故事

### 5.1 登录/退出模块

> **US-01**：作为管理员，我希望通过账号密码登录管理后台，以便安全地访问系统管理功能。

> **US-02**：作为内部员工，我希望系统在我长时间未操作时自动退出，以便防止他人盗用我的会话操作后台。

> **US-03**：作为管理员，我希望在登录时如果连续输错密码 5 次，账号会被临时锁定，以便防止暴力破解攻击。

> **US-04**：作为内部员工，我希望点击"退出登录"后立即清除会话并返回登录页，以便在共用电脑时保护账号安全。

### 5.2 员工管理模块

> **US-05**：作为管理员，我希望在员工管理页面按姓名/手机号搜索员工，以便快速定位目标员工信息。

> **US-06**：作为管理员，我希望新增员工时填写姓名、手机号、登录账号、初始密码、角色等信息，以便为不同岗位的员工分配对应权限的账号。

> **US-07**：作为管理员，我希望编辑员工信息时可以修改角色和联系方式，但不能修改登录账号（唯一标识），以便保持账号体系稳定。

> **US-08**：作为管理员，我希望可以禁用某员工的账号而非直接删除，以便保留其历史操作记录，同时阻止其继续登录。

### 5.3 分类管理模块

> **US-09**：作为运营人员，我希望查看所有菜品分类和套餐分类的列表，以便了解当前餐厅的分类体系。

> **US-10**：作为运营人员，我希望新增分类时可以指定类型（菜品/套餐）和排序权重，以便控制分类在前台的展示顺序。

> **US-11**：作为运营人员，我希望修改分类名称时系统检查该分类下是否有关联菜品/套餐，以便避免误删导致菜品归属丢失。

> **US-12**：作为运营人员，我希望删除分类时如果有关联菜品/套餐，系统阻止删除并提示"请先移除关联菜品"，以便防止数据孤儿。

### 5.4 菜品管理模块

> **US-13**：作为运营人员，我希望按分类筛选菜品列表，以便快速查看某个分类下的所有菜品。

> **US-14**：作为运营人员，我希望新增菜品时可以填写名称、分类、价格、描述、图片，以便顾客在前台看到完整的菜品信息。

> **US-15**：作为运营人员，我希望对菜品执行"启售/停售"操作，以便在缺货或临时调整时快速控制菜品可见性，而无需删除菜品信息。

> **US-16**：作为运营人员，我希望批量启售/停售选中的菜品，以便在节假日或临时歇业时一键操作多个菜品。

### 5.5 套餐管理模块

> **US-17**：作为运营人员，我希望新增套餐时可以选择多个菜品组成套餐并设置套餐价格，以便通过组合销售提升客单价。

> **US-18**：作为运营人员，我希望编辑套餐时可以增删套餐内的菜品，并自动重新计算价格建议值，以便快速调整套餐内容。

> **US-19**：作为运营人员，我希望对套餐执行"启售/停售"操作，以便在套餐内某菜品缺货时暂停整个套餐销售。

### 5.6 订单管理模块

> **US-20**：作为客服，我希望按订单号/手机号/订单状态搜索订单，以便快速响应用户的订单咨询。

> **US-21**：作为客服，我希望在订单详情页查看完整的订单信息（菜品明细、金额、支付方式、配送地址），以便准确判断问题原因。

> **US-22**：作为运营人员，我希望对待派送订单执行"派送"操作将订单状态更新为"派送中"，以便配送环节及时跟进。

> **US-23**：作为运营人员，我希望将已完成的订单状态标记为"已完成"，以便订单进入结算和数据统计流程。

> **US-24**：作为客服，我希望对用户取消的订单执行"取消"确认操作，以便触发退款审核流程（如已支付）并释放库存。

> **US-25**：作为管理者，我希望下载指定时间段的订单报表（Excel 格式），以便进行线下分析和归档。

### 5.7 数据统计模块

> **US-26**：作为管理者，我希望在数据统计首页查看当日营业额、订单量、用户数等核心指标，以便快速了解当日经营概况。

> **US-27**：作为管理者，我希望查看近 7 天/30 天的营业额趋势折线图，以便发现经营趋势和异常波动。

> **US-28**：作为管理者，我希望按菜品维度查看销量排行 TOP 10，以便优化菜品结构和备货策略。

| 优先级    | 需求编号 | 需求描述     | 验收标准                                     |
| ------ | ---- | -------- | ---------------------------------------- |
| **P0** | L-01 | 账号密码登录   | 输入正确账号+密码 → 登录成功，跳转首页；输入错误 → 提示"账号或密码错误" |
| **P0** | L-02 | 登录态校验    | 未登录状态访问任意后台路由 → 自动重定向至登录页                |

| **P1** | L-06 | 登录失败锁定   | 同一账号连续 5 次密码错误 → 锁定 30 分钟，期间不可登录         |
| **P2** | L-07 | 验证码登录    | 支持手机短信验证码登录，作为密码登录的备选方式（v2）              |

## 9. 时间线考量

### 9.1 关键依赖

| 依赖项      | 说明                        | 阻塞的模块            |
| -------- | ------------------------- | ---------------- |
| 数据库设计与建表 | 员工表、分类表、菜品表、套餐表、订单表、统计视图等 | 全部模块             |
| 支付系统状态对接 | 订单管理需展示支付状态，但不涉及支付网关开发    | 订单管理（O-02, O-05） |
| 前台菜品同步机制 | 后台菜品变更后前台需及时刷新            | 菜品管理、套餐管理        |

### 9.2 建议分阶段交付

| 阶段                 | 范围                  | 说明                             |
| ------------------ | ------------------- | ------------------------------ |
| **Phase 1 — 基础骨架** | 登录/退出 + 员工管理 + 分类管理 | 搭建权限体系和基础数据结构，是后续模块的前置依赖       |
| **Phase 2 — 核心业务** | 菜品管理 + 套餐管理         | 依赖分类管理的数据，是订单流转的前置条件           |
| **Phase 3 — 运营闭环** | 订单管理                | 依赖菜品/套餐数据，是数据统计的数据来源           |
| **Phase 4 — 数据驱动** | 数据统计                | 依赖订单数据积累，建议在 Phase 3 上线 1 周后交付 |

### 9.3 硬性节点

- **支付系统联调**：订单管理中的支付状态展示需等待支付系统对接完成，如果支付系统延迟，O-02/O-05 中的支付状态字段暂时展示"待对接"占位。退款流程为人工审核后原路退回，需确保支付系统的退款 API 可用。
- **前台联调**：菜品/套餐管理的前台同步效果需与前端团队联调，建议 Phase 2 完成后立即启动前后台联调。

## 10. 技术考量与约束

| 维度        | 约束/建议                                                                                 |
| --------- | ------------------------------------------------------------------------------------- |
| **前端技术栈** | 管理后台建议使用 Vue.js + Element UI（或 Ant Design Vue），与项目整体前端技术栈一致                           |
| **后端技术栈** | Spring Boot + MyBatis-Plus，MySQL 数据库，Redis 缓存（会话管理 + 菜品列表缓存）                          |
| **安全合规**  | 密码加密存储（BCrypt）；登录态基于 JWT + Redis；接口需防 SQL 注入（MyBatis 参数化查询）；员工数据涉及个人信息，需符合《个人信息保护法》要求 |
| **接口规范**  | 统一返回格式 `{code, msg, data}`；统一异常处理；分页统一使用 `page` + `pageSize` 参数                       |
| **部署要求**  | 管理后台前端 Nginx 部署，后端 Jar 包以 systemd 服务（`myapp`）运行在 Ubuntu 服务器上                          |

## 11. 风险与缓解

| 风险              | 影响             | 缓解措施                                |
| --------------- | -------------- | ----------------------------------- |
| 支付系统对接延期        | 订单管理无法展示完整支付状态 | Phase 3 订单管理先上线不含支付状态的版本，支付状态作为增量迭代 |
| 菜品/套餐数据量大时列表查询慢 | 菜品管理页面加载超过 3 秒 | 菜品列表加分类索引 + Redis 缓存；分页默认 10 条/页    |
| 多人同时编辑同一菜品      | 数据覆盖/不一致       | 后端乐观锁（version 字段）或编辑时锁定             |


| 员工误操作删除分类导致菜品归属丢失 | 菜品在前台无分类展示 | 删除分类前强校验关联菜品；菜品软删除而非物理删除 |  
| 服务器资源有限（2 核 2G） | 高峰期后台响应慢 | 数据统计查询使用定时任务预计算，避免实时聚合查询 |

## 附录 A：术语表

| 术语  | 定义                                       |
| --- | ---------------------------------------- |
| 启售  | 将菜品/套餐状态设为"在售"，前台可被顾客浏览和下单               |
| 停售  | 将菜品/套餐状态设为"停售"，前台不展示，但后台数据保留             |
| 软删除 | 数据库记录标记 `is_deleted=1`，不物理删除，列表查询过滤已删除记录 |
| 派送  | 订单状态从"待派送"流转为"派送中"，表示已通知配送取货             |
| 营业额 | 统计周期内已完成订单的实付金额总和 **扣除已退款金额后的实收净额**（不含已取消订单） |
| GMV | 统计周期内所有下单金额总和（含未完成/已取消订单）                |

## 附录 B：订单状态流转图

```
                    ┌─────────┐
                    │  待接单   │ ← 用户下单
                    └────┬────┘
                         │ 接单
                         ▼
                    ┌─────────┐
        ┌───────────│  待派送   │
        │            └────┬────┘
        │ 取消             │ 派送
        ▼                 ▼
  ┌─────────┐       ┌─────────┐
  │  已取消   │       │  派送中   │
  └────┬────┘       └────┬────┘
       │                 │ 完成
       │ 已支付?          ▼
       ▼            ┌─────────┐
  ┌─────────┐       │  已完成   │
  │ 退款审核  │       └─────────┘
  └────┬────┘
       │ 审核通过
       ▼
  ┌─────────┐
  │ 原路退款  │
  └─────────┘
```

> **说明**：待接单/待派送状态可取消；派送中状态一般不可取消（特殊场景需人工介入）；已完成不可取消。已支付的订单取消后，进入**人工退款审核流程**，审核通过后资金**原路退回**（按原支付方式退还）。
